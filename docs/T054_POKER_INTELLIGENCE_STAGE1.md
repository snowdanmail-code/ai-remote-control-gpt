# T054 — Покерный интеллект: контрольный этап 1 (статистика соперников)

Дата: 15 ноября 2026. Ветка: `feature/t043-gpt-decision-contract`, draft PR №8.

## Исправление

**Проблема:** старый реестр принимает только подтверждённые наблюдения и
часто оставляет отсутствие VPIP/PFR как `null`. Заменить `null` на
`false` небезопасно: пропуск кадра или нераспознанный префлоп
не являются доказательством пассивного действия.

**T054VerifiedOpponentOpportunities:** отдельный pure-Kotlin расчёт.
- Полная **независимо подтверждённая** история префлопа + доказательство
  участия игрока в раздаче разрешают истинные отрицательные знаменатели
  VPIP/PFR.
- Рейз доказывает положительный PFR и VPIP; колл — только VPIP.
- Обязательные блайнды и анте сами по себе НЕ означают добровольный вход.
- Если история неполная, неподтверждённые отрицательные исходы остаются
  `null`; они не добавляются в знаменатель.
- Некорректные/неподтверждённые события и дубли `eventId` отклоняются.
- Если в одной раздаче было несколько событий facing-bet, отдельные
  количества фиксируются в результате нового расчёта; старое поле
  `foldedWhenFacingBet: Boolean?` оставляется неизвестным. Сведение
  двух решений к одному Boolean исказило бы частоту фолдов.

**LiveOpponentAwareness:** теперь в существующем runtime на одном
подтверждённом faced-bet CALL/RAISE ставит `foldedWhenFacingBet=false`,
а на FOLD — `true`. При двух и более подтверждённых решениях
перед лицом ставки возвращает `null` вместо прежнего ложного `true`
в случае хотя бы одного FOLD.

## Важное ограничение

`T054VerifiedOpponentOpportunities` теперь подключён к
`PostHandLearner.onHandFinished` через необязательное поле
`VerifiedFinishedHand.verifiedOpponentOpportunities`. Данные принимаются
только при завершённой верифицированной раздаче, точном совпадении
`opponentKey` с уже известным участником и отсутствии конфликтов с
имеющимися фактами. Исходный транскрипт после нормализации не
сохраняется в существующем SQLite v2.

**Реальный signed full-preflop транскрипт в приложении по-прежнему
не вырабатывается.** Это подготовленный вход для будущего проверенного
hand/table/actor-bound источника, а не разрешение конструировать
`complete=true` из OCR. Нельзя объявлять 0/1 из скриншотов
подтверждённым шансом VPIP/PFR.

Формат старой SQLite v2 всё ещё хранит fold-to-bet не более одного
Boolean на раздачу, а не число возможностей/фолдов. Для честной
многостадийной статистики потребуется отдельная миграция v3
с `facing_bet_opportunities` и `folds_to_bet` **внутри одной раздачи**,
плюс тест с сохранением старых данных.

## Приёмочные сценарии

- Полная, verified PREFLOP: POST_BLIND + FOLD -> VPIP=false, PFR=false.
- Только подтверждённый FOLD в неполной истории -> оба null.
- Verified RAISE в неполной истории -> оба true.
- Проверенный CALL без RAISE в полной истории -> VPIP=true, PFR=false.
- Один facing-bet CALL -> Fold-to-Bet=false; один FOLD -> true.
- Facing-bet CALL и позднее FOLD в одной раздаче -> v2 Boolean=null.
- Дубликаты и непроверенные события -> отвергнуть, не сохранять.
- Запустить JVM сценарии и Android unit-тесты на актуальном SHA.

## Безопасность и регрессия

Изменения не расширяют права Accessibility, не снимают STOP,
не разрешают автоматические ставки/бай-ин и не меняют старую
таблицу SQLite. Неподтверждённый факт остаётся неизвестным.
